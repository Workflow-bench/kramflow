# KramFlow — Senior QA + UI/UX Audit Report

**Scope:** `deep` branch, commit `7b1ebe9` ("bug fix after shibir"), tested locally via `npm run dev` against a live Supabase backend.
**Method:** Real browser interaction (Chromium via Claude's Browser tool) across `/operator`, `/remote`, `/green-room`, `/av`, `/general`, `/presenter`, `/broadcast`, `/display-manager`, plus source-code verification for every finding below. Multiple tabs were held open simultaneously to observe cross-surface sync in real time. Supabase state was inspected directly via SQL where useful (activity_log, live_state, display_broadcasts, display_registry).

With the user's approval, I provisioned a **temporary Supabase project** (`kramflow-qa-temp`, `lwgclskcrovknivdxvog`) via the Supabase MCP tools already available in this session: applied `supabase/schema.sql`, ran `npm run seed` (6 sessions, 244 programs — close to the README's "~250 cues"), and pointed `.env.local` at it. **`.env.local` on disk now points to this temp project**, not the original dead one — the user should either keep using it or swap in real credentials before further work. ## 1. Executive summary

**Readiness: not yet — ships with real gaps that would surface at a live event.** The core loop (Next/Previous/Jump/Hold/Alert/Notes, session-per-session progress, cross-device Realtime sync) is solid and well-engineered — genuinely cross-device now via Supabase, with thoughtful optimistic-concurrency and double-submit guards in most places. But there are two Blocker/Critical-grade bugs that would actively hurt a live show, plus a meaningful accessibility and responsive-design gap, and the README/prompt's own description of the app is stale enough to have sent this audit down the wrong route table initially.

**Top 5 risks, in priority order:**

1. **BUG-1 (Blocker):** The Operator's "Raise Alert" feature — a core, documented capability ("appears instantly on every TV") — never renders on the **Green Room** or **General** displays. It only shows on AV, Presenter, and the operator's own screen. An urgent "Drama Team, report to Stage Left NOW" alert would never reach the performers it's most likely aimed at.
2. **BUG-2 (Critical):** The Operator Dashboard's session-switcher becomes **invisible and unclickable** at 1280px viewport width (Tailwind's `xl` breakpoint, a completely ordinary laptop resolution) — its flex container computes to `width: 0`. Operators cannot switch sessions at this width without resizing the window.
3. **BUG-3 (Critical):** The Operator Dashboard's embedded emergency-broadcast confirm (Evacuate/Fire/Medical presets) has **no double-submit guard**, unlike the identical, already-fixed flow in Broadcast Center. Rapid clicks send duplicate persistent, acknowledgement-required emergency takeovers to every display — reproduced live (3 concurrent clicks → 3 duplicate "EVACUATE BUILDING"-class broadcasts).
4. **SEC-1 (security hygiene, already being remediated by the user):** Real Supabase URL, anon key, service-role key, and the auth cookie secret were committed in plaintext to `.env.example` in git history. A fix is staged but uncommitted.
5. **BUG-4/BUG-5 (Major):** Display Manager's "Test Message" remote command is a no-op on **every** display (none of the 4 display pages handle `command.type === "test-message"`); "Force Fullscreen" only works on Presenter. Both are documented Display Manager features.

Everything else — PIN auth (including rate limiting), Hold/Pause timing precision, session-independent progress, notes propagation, alert dismiss/refresh-persistence, Next/Previous/Jump boundary handling, XSS safety on the alert composer — held up well under adversarial testing. See §5 for the positive findings, which are numerous and worth knowing about too.

**Documentation is stale relative to the code.** The QA prompt's route table (based on the README) describes a `NEXT_PUBLIC_DISPLAY_ENGINE_ENABLED`-gated launcher and `/displays/*` routes. Neither exists anymore — the flag was removed and routes consolidated to `/presenter`, `/green-room`, `/av`, `/general` during a documented refactor (`docs/DISPLAY_ENGINE.md`'s "History" section says this explicitly). `docs/ARCHITECTURE.md`/`DATA_MODEL.md`/`DISPLAY_ENGINE.md` are accurate and were used as ground truth instead; `README.md`'s "Tech Stack" and "Roadmap" sections are the stale ones (still describe `localStorage`/`BroadcastChannel` as current sync with "Supabase Realtime" as a future step, when Supabase is already fully live).

## 2a. Non-bugs worth flagging as testing-environment noise

- **`ConfirmDialog` exit-animation lag:** After confirming an action (Start, Jump, Switch Session, Finish Session), the dialog remains present in the accessibility tree/DOM for a brief moment during its 250ms Framer Motion exit transition, occasionally causing an immediate follow-up click to land on nothing. This is cosmetic (the underlying action always completed correctly in every case checked) and not a functional bug, but it's a real timing window — a very fast double-click right after confirming one dialog and immediately opening another could plausibly eat a click. Not scored as a bug since no incorrect state was ever observed, but worth a UX pass if it comes up again.
- **`live_state.updated_at` never changes:** The column exists in the schema but no API route (`app/api/live/route.ts`) ever sets it — only `version` is bumped. Harmless (activity_log's `created_at` is the real audit trail) but the column is dead weight/misleading if anyone queries it expecting a real timestamp.

## 5. Sync/state findings

This is the product's core mechanic, so it got the most adversarial testing. All of the following were verified **live**, with multiple tabs open simultaneously (`/operator` + `/green-room` + `/av` + `/general` + `/presenter`), not inferred from code:

- **Cross-surface propagation, happy path:** Next/Previous/Jump/session-switch/notes edits all appeared on every open public display within roughly a second, matching the README's claim. Directly observed via paired before/after screenshots across tabs.
- **Session-per-session progress isolation:** Started Friday, advanced it to item 3, switched to Saturday Morning, started and advanced *that* independently to item 2, switched back to Friday — Friday was exactly where it was left (3/24, correct item live), confirmed via `progress_by_session` in the DB (`{"friday-evening-session":{"currentOrder":24,...},"saturday-morning-session-1-2":{"currentOrder":2,...}}` after further advancing). Works correctly.
- **Hold/Pause timing precision:** Engaged Hold, confirmed the countdown froze at the *exact same second* on Green Room and AV simultaneously (both showed `20:11` while the wall clock kept advancing), waited 3 real seconds and re-confirmed it hadn't drifted, then resumed and confirmed the countdown continued from `20:11` with no jump or loss — the shift-on-resume math in `app/api/live/route.ts`'s `togglePause` works as documented.
- **Double-submit guard, verified not just claimed:** A genuine rapid double-click on Next produced exactly one `PATCH /api/live` call (button disables synchronously during the pending request) — advanced exactly one item, not two, both times tested.
- **Optimistic concurrency:** Not exhaustively raced, but the version-check/409-retry mechanism in `app/api/live/route.ts` was read and is sound (read-version → write-with-version-match → 409 on mismatch → client retries once).
- **Alert dismiss propagates:** Dismissing from the operator cleared the banner on AV within the same ~1s window.
- **Alert survives a hard refresh:** Posted an alert, hard-refreshed `/av` (not just SPA nav), and the alert reappeared correctly from server state — not client-only ephemeral state.
- **XSS safety, verified not just assumed:** Posted an alert containing `<script>alert('xss')</script>` plus emoji and `<b>bold</b>` — rendered as inert plain text everywhere it appears (operator's own panel, AV, Presenter); no script execution, no HTML interpretation. React's default text-escaping is doing its job; no `dangerouslySetInnerHTML` in the alert-rendering path.
- **PIN/session security enforced server-side, not just hidden client-side:** After clicking "Lock," directly POSTed to `/api/live` with the old (now-revoked) browser session and got a real `401` — confirmed the `DELETE /api/auth` call actually revokes the signed cookie server-side, not just the client-side `sessionStorage` flag that drives the PIN screen's visibility.
- **Rate limiting works exactly as documented:** 8 wrong PIN attempts triggered a `429` with `retryAfterSeconds` (even for the *correct* PIN, while locked — correct behavior for an IP-level lockout), confirmed via direct API calls.
- **Silent failure with no backend:** When Supabase was unreachable (the original state — see §0), `lib/store.tsx` and `lib/use-sessions.ts` only `console.error` the failure; there's no user-facing error/retry UI anywhere in the fetch/hydrate path. An operator opening the dashboard during a real outage would see... nothing informative (not independently screenshotted in this session since the backend was fixed before I got to that specific check, but the code path is unambiguous: no error state exists to render).

**Explicit callout the prompt asked for:** genuine cross-*device* sync (not just cross-tab-same-browser) could not be tested in this environment — every "device" here was a tab in the same browser hitting the same Supabase project over the network, which does exercise the real Realtime/Postgres path (not `localStorage`/`BroadcastChannel`, which the architecture doc confirms is only used for the local-only Profiles/Groups slice now), but a literal second physical device on different WiFi was not available to test.

## 6. Open questions / things not independently verified

- **Real dataset accuracy:** Cue-sheet parsing logic (column resolution, break-row detection, section-label attachment) was spot-checked against `data/cue-sheet.xlsx` directly and matched the seeded DB exactly for the rows checked (names, presenters, times, durations, notes). A full row-by-row diff of all ~244 rows across all 6 sheets was not performed.
- **Genuine multi-device sync** — see above; only same-browser-multi-tab was exercised, against a real network backend.
- **Broadcast Center's non-emergency flows** (scheduling, templates, drafts, history, per-display/per-group targeting) were read in source and are consistent with the docs, but not clicked through live — time was spent on the emergency-preset bug (BUG-3) instead, which was the higher-value find.
- **Browser matrix:** only tested in one Chromium-based browser via the automation tooling available; Safari/WebKit (relevant since Smart TVs are often WebKit-based) was not tested.
- **Performance/re-render profiling** of the dense Operator Dashboard was not done with React DevTools Profiler (not available in this environment) — no re-render thrashing was *observed* incidentally during testing, but this wasn't specifically instrumented.
- **The temp Supabase project's RLS is intentionally not representative of production** (see §0) — anything about write-permission edge cases specific to the real service-role-key path should be spot-checked against the real production project once one exists.
