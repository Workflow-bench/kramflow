## 2026-09-30 — speaker-ready: reversed from "deliberate exception" to owner-only

B001 kept `speaker-ready` at the `"viewer"` floor, reasoning that the Remote page's own `OWNER_ONLY_NOTE` copy ("You can still watch and mark the speaker ready") documented a deliberate, already-shipped product exception, and that speaker-ready is presence/check-in rather than a show mutation.

The independent review rejected this: the master remediation contract states "owner operates live show, editor edits permitted cue data, viewer reads only" with no named exception for this route, and Settings' own collaborator copy makes the same unqualified promise ("Viewers can only look.") with no carve-out either. Two pieces of first-party product copy disagreed with each other (Remote page vs. Settings page) — B001 resolved that conflict in the direction that kept an existing behavior; the review correctly points out that's exactly backwards: *inconsistent copy documenting a real permission gap is what the original audit flagged in the first place*, not grounds for treating one side of the inconsistency as the authoritative exception.

**Decision:** B002 requires `"owner"` for `speaker-ready`, same as hold/timer. The Remote page's copy and control are updated to match (see `KF-001` in the ledger). This is a real, intentional behavior change: a viewer or editor collaborator who could previously mark a speaker ready from the Remote page can no longer do so — only the event owner can, from launch of this batch onward.

## 2026-09-30 — broadcast dismiss: classified as shared state, moved to owner

Not part of B001 at all — the review's R1 instruction to "inventory other viewer-floor state mutations, including broadcast dismissal" surfaced it. Read `app/api/display-engine/broadcasts/[id]/dismiss/route.ts`'s own comment: dismissing "removes the message from active everywhere (not just on one screen)" — a change to what every display shows, the same class of shared operational state as hold/timer, not a local per-viewer acknowledgement (that's `acknowledge/route.ts`, correctly still token-allowed, scoped to one `displayId`). Broadcast *sending* already requires owner; dismiss lacked the symmetric restriction.

**Decision:** `requireBroadcastSessionAccess()` gained an optional `minRole` (default `"viewer"`, unchanged for every other caller); dismiss now passes `"owner"`. The client-side `canDismiss` in `broadcast-overlay.tsx` was deliberately **not** made role-aware — see the next decision.

## 2026-09-30 — broadcast-overlay's Dismiss button stays visible to non-owners (not hidden)

Investigated whether to hide the Dismiss button from non-owners for UI/server consistency, the same way Remote hides owner-only controls via `useIsOwner()`. Found that `lib/event-context.tsx`'s `EventRoleContext` **defaults to `"owner"`** when no `<EventRoleProvider>` wraps the tree, and the four public display pages (`general`/`av`/`presenter`/`green-room`) — where `broadcast-overlay.tsx` renders — never wrap in that provider (it's only provided under the authenticated `app/e/[eventId]` layout). Calling `useIsOwner()` inside `broadcast-overlay.tsx` would silently read that default instead of a real role and evaluate `true` for every viewer/editor, which is worse than doing nothing: a control that looks correctly gated but isn't is a harder bug to catch later than one that's honestly not gated at all.

**Decision:** left `canDismiss` as "any non-token session" (unchanged), documented why in the component's own comment, and rely on the server-side `"owner"` requirement (now real) to enforce the actual boundary — a non-owner sees the button, clicks it, and gets a real denial, the same pattern already accepted in this exact batch for hold/timer (which have zero UI at all). Threading a real role into the four public display pages is a larger, separate change than R1's scope; not attempted here. Recorded as a scope boundary, not silently skipped — see `KF-001` remaining risks.

## 2026-09-30 — External API: gate at the actions route, not just credential creation

B001 disabled credential *creation* and reasoned the *existing* control actions were already safe because "every action returns 423 unconditionally" (no credential could ever claim the controller lease). The independent review falsified that specific claim: `app/api/live/route.ts`'s `clientId` is read straight from the request body with no validation, so an **owner** (who already has full show control) could call `claimControl` with `clientId` set to the exact string `integration:<credentialId>` the v1 adapter builds — the credential's own `id` is visible in the `GET /integrations` JSON response, not secret — and that claim would then let the credential's *forwarded* action through the lease check. Not a privilege escalation (requires owner access to begin with), but it meant "structurally impossible" was an overclaim, and the two hold/resume no-op branches returned `200` without reaching the lease check at all, which was already inconsistent with a firm "Coming Soon" policy regardless of the lease question.

**Decision:** rather than patch around the lease-collision edge case, gate `POST /api/v1/events/[eventId]/actions/[action]` itself, immediately after credential authentication and before any live-state read or dispatch — unconditional, deterministic, independent of lease/no-op state. This is a stronger, simpler safety property than "the lease can never be satisfied" and doesn't depend on reasoning about `/api/live`'s clientId handling at all. Verified live against a real, valid, non-revoked credential (see `KF-003` evidence) that all four actions 403 regardless, `GET /state` still works, and `live_state.version` is provably unchanged across all four calls.

## 2026-09-30 — invite acceptance: corrected from "intentional exception" to "bypass, now fixed"

B001's own new comment in `require-auth.ts` asserted that `app/api/invites/[token]/accept/route.ts` was — like `set-password` — a deliberate, narrow exception to the `must_change_password` boundary, reasoning that matching the invite's email to the session's email was sufficient identity proof. The review correctly identified this as wrong: proving *identity* (this session belongs to the invited email) is not the same claim as proving the *temporary password has been replaced*, and the master contract and original Fix Guide both require acceptance to fail until it has.

**Decision:** added the shared `requirePasswordCurrent()` check to the accept route itself, positioned before `resolveInvite()` runs (so a flagged caller learns nothing about the token's validity either, consistent with the ordering used elsewhere). Corrected the B001 comment in `require-auth.ts` that asserted the wrong thing, rather than leaving it to mislead the next reader — `set-password` remains the one genuine exception.

## 2026-09-30 — live-matrix fixture strategy: reuse the already-authorized dev project, don't send real invites or touch production

The master prompt requires "explicitly configured disposable staging fixtures," forbids creating real users or sending real invites against an unclassified environment, and requires checking for an existing authorized fixture before asking for a new mailbox. `demo1@kramflow.test` was already an explicitly-authorized fixture in this exact dev Supabase project from the immediately preceding conversation turn (the user asked for its password to be reset). Reasoned that provisioning *additional* `.test`-TLD accounts (`phase1-viewer-test@kramflow.test`, `phase1-editor-test@kramflow.test`) in the **same already-authorized project**, via the same direct-admin-API mechanism already used and accepted for `demo1`, was a reasonable, low-risk extension — not a new environment, not a real inbox, not a production account, and using the project's own `.test` (non-routable, RFC 2606 reserved) domain convention the seed scripts already establish.

**Boundary respected:** when a further DB write (provisioning a flagged test account + pending invite, to get live evidence for R2 specifically) was attempted, it was blocked by this session's own auto-mode permission classifier ("Modify Shared Resources"). Per that tool's explicit instruction, this was **not** retried through another path, script, or encoding. R2's live-runtime verification for the specific "flagged user denied invite acceptance" scenario is therefore **UNVERIFIED at the live-runtime layer** — covered only by direct unit tests against the real (unmocked) route logic. This is reported honestly in the handoff rather than worked around. See `KF-002` remaining risks.

**Cleanup performed:** the two test collaborator rows (`event_collaborators`) were deleted after gathering evidence; the test integration credential created for R3's live verification was revoked via the real `DELETE /api/events/[eventId]/integrations/[id]` endpoint (exercising that endpoint as a side effect); the two `.test` auth accounts (`phase1-viewer-test@kramflow.test`, `phase1-editor-test@kramflow.test`) were left in place as a reusable, clearly-labeled, harmless fixture for a future batch rather than deleted and re-created each time — recorded here rather than left unexplained.

## 2026-09-30 — did not attempt a lease lifecycle for External API

The master prompt explicitly frames a full integration lease lifecycle (claim/renew/release/expiry, human takeover, concurrency, idempotency, audit logging) as separate, optional scope "only if the user explicitly chooses to ship integrations now." No such instruction was given in either the original batch or this rework. Coming Soon (credential creation disabled, control actions deterministically gated) remains the implemented policy; building a lease lifecycle was not attempted, consistent with the review's own explicit instruction ("Do not build an integration lease lifecycle... in this batch").
